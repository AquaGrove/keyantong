# 13 · 运维 Runbook

**状态：** Accepted  
**版本：** v0.1

## 1. 日常巡检（每日/每周）

| 频率 | 项 |
|------|----|
| 日 | Uptime、磁盘、备份是否成功、LLM 费用 |
| 周 | 失败 Job 抽样、AI 胡编抽检、安全更新 |
| 季 | 备份恢复演练、证书与密钥轮换检查 |

## 2. 健康检查端点（目标）

| 服务 | 路径 | 期望 |
|------|------|------|
| Portal | `/` 或 `/api/health` | 200 |
| RAG | `/healthz` | 200；可含依赖探测 |
| Analysis | `/healthz` | 200 |
| Forum | 上游健康页 | 200 |

## 3. 发布流程

1. 合并到 `main`（CI 绿）  
2. 打 tag（可选）  
3. staging 部署并冒烟：发帖、suggest、登录  
4. 生产：先迁移 DB（向后兼容）再滚服务  
5. 观察 15–30 分钟错误率  

论坛升级：**单独维护窗口**，先快照再升，遵循上游版本说明。

## 4. 回滚

| 组件 | 回滚方式 |
|------|----------|
| Portal / API 镜像 | 切回上一 tag 并重启 |
| DB 迁移 | 仅当有经过测试的 down；否则前向修复 |
| 论坛 | 恢复快照卷；勿盲目降级跨越多版本 |
| 功能开关 | `AI_SUGGEST_ENABLED=false` 即时止血 |

## 5. 故障手册

### 5.1 站点无法访问

1. 查云主机 / 安全组 / 带宽  
2. `docker ps` / 反代状态  
3. 证书是否过期  
4. 若仅门户挂、论坛仍在：DNS 与反代分流排查  

### 5.2 发帖正常但 AI 无建议

1. 查 `AI_SUGGEST_ENABLED`  
2. Webhook 日志与验签  
3. LLM 额度/网络  
4. 向量库连接  
5. 对用户保持降级静默，不必公告除非大面积失败  

### 5.3 数据库磁盘满

1. 扩容或清日志  
2. 确认 OSS 是否误写本地  
3. 真空/归档旧 Job 产物元数据  

### 5.4 疑似内容侵权

1. 下架相关帖/附件  
2. 保留证据与处理记录  
3. 回复权利人（法务流程）  
4. 复盘入库与上传策略  

### 5.5 密钥泄漏

1. 立即轮换（LLM、OSS、Webhook、DB）  
2. 查访问日志  
3. 作废旧密钥  
4. 通知相关协作者  

## 6. 备份恢复（摘要）

```bash
# 示例：PostgreSQL 恢复（具体脚本以 infra/ 为准）
pg_restore -d keyantong backup.dump
```

恢复后：校验用户桥接表、随机抽查帖子镜像、跑一次 suggest。

## 7. 值班与升级

- MVP：负责人手机告警（Uptime）  
- 定义 Sev1（全站不可用）/ Sev2（AI 全挂）/ Sev3（单工具失败）  
- Sev1 目标：30 分钟内有人响应  

## 8. 变更窗口建议

- 工作日低峰；避开投稿/组会高峰若已知  
- 大版本论坛升级提前公告
