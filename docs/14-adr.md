# 14 · 架构决策记录（ADR）

**状态：** Accepted（目录）  
**版本：** v0.1

ADR 用于记录「当时为什么这样选」。格式统一，拍板后只追加，不删改历史；若推翻则新建 ADR 并标记旧条 `Superseded`。

## ADR 模板

```markdown
# ADR-XXX: 标题

- 状态: Proposed | Accepted | Superseded by ADR-YYY
- 日期: YYYY-MM-DD
- 决策人:

## 背景

## 决策

## 后果

## 备选方案
```

## ADR-001: 论坛引擎选型

- 状态: **Accepted**  
- 日期: 2026-08-25  
- 决策人: 项目负责人  

### 背景

科研通 MVP 以社区为核心，需在 Discourse 与 NodeBB 间选择，避免自研论坛。算力与运维成本需可控，并与 TypeScript 自研服务栈对齐。

### 决策

采用 **NodeBB** 作为论坛引擎。

### 后果

- 建议起步规格 **2C4G**（低于 Discourse 的 8G 建议）  
- 插件与 Webhook 按 NodeBB 上游实现；配置覆写放在 `forum/nodebb/`  
- 12 个月内原则上不更换引擎；若更换须新 ADR 并标记本条 Superseded  

### 备选方案

- Discourse：运营/SEO 更强，但内存占用高——否决（当前资源与同栈优先级）  
- Flarum、自研：否决（生态或成本不适合 MVP）  

---

## ADR-002: MVP 优先论坛而非独立 RAG 机器人

- 状态: **Accepted**  
- 日期: 2026-08-24  

### 背景

存在两条启动路径：先做文献互助论坛，或先做科研问答机器人。

### 决策

采用 **论坛优先 + 发帖场景轻量 RAG 初答**；不把独立聊天机器人作为 MVP。

### 后果

- 内容资产与 SEO 起步更实  
- RAG 依赖种子帖与审核入库，冷启动需运营  
- AI 以插件/侧栏建议形态出现  

### 备选方案

纯 RAG 机器人：否决（缺自有语料、难留存、与贡献激励冲突）。

## ADR-003: LLM 使用外部 API，MVP 不自托管大模型

- 状态: **Accepted**  
- 日期: 2026-08-25  

### 背景

需控制成本与运维复杂度，同时验证初答价值。

### 决策

生成走外部 LLM API；Embedding 可用 API 或 CPU 小模型；不采购 GPU。

### 后果

有按量费用与供应商依赖；通过预算告警与开关控制风险。

### 备选方案

自托管 7B+：推迟至有明确 ROI。

## ADR-004: 分析与业务库权威分离，论坛库不直写

- 状态: **Accepted**  
- 日期: 2026-08-25  

### 背景

多子系统易出现跨库脏写。

### 决策

帖子权威在论坛；积分/工具/Job 在自研 PG；集成仅 API/Webhook/官方插件。

### 后果

有一定同步延迟与工程量；换论坛版本更安全。

## ADR-005: 部署形态 —— 国内 VPS 为主，Zeabur 为辅

- 状态: **Accepted**  
- 日期: 2026-08-25  

### 背景

需兼顾备案/延迟与快速部署。

### 决策

论坛与数据库放国内 VPS；门户或无状态服务可放 Zeabur；重算后期独立节点。

### 后果

运维需熟悉 Compose；避免过早上 K8s。

## ADR-006: 主仓库采用 Apache License 2.0

- 状态: **Accepted**  
- 日期: 2026-08-25  
- 决策人: 项目负责人  

### 背景

科研通以开源共享为宗旨，需选定适合大型协作、含专利授权条款的 OSI 许可。计划草案曾称 ADR-003，因编号已被「外部 LLM」占用，故记为 ADR-006。

### 决策

主仓库与默认贡献许可为 **Apache-2.0**（见根目录 `LICENSE` / `NOTICE`）。

### 后果

- 贡献默认同许可（见 `CONTRIBUTING.md`）  
- NodeBB 等上游仍遵循其各自许可证  
- 工具卡需声明自身 `license` 字段  

### 备选方案

MIT：更短但专利条款弱——未选。GPL：对插件生态传染性强——未选。

## ADR-007: Monorepo 与分层贡献模型

- 状态: **Accepted**  
- 日期: 2026-08-25  
- 决策人: 项目负责人  

### 背景

大型长期项目需单一协作入口，同时让「不会写核心代码」的人也能贡献。计划草案曾称 ADR-004，因编号已被「库权威分离」占用，故记为 ADR-007。

### 决策

1. 采用 **pnpm workspace + Python services** 的 Monorepo（`apps/` `services/` `packages/` `catalog/` `forum/` `infra/`）  
2. 分层贡献：论坛回答 → `catalog/tools` YAML → `docs/` → 代码 PR  
3. 本地最小依赖：`infra/docker-compose.dev.yml`（Postgres/Redis）+ `scripts/smoke.sh` + CI  

### 后果

- 贡献路径写在 `CONTRIBUTING.md` / `docs/12-contribution.md`  
- 子系统可独立扩缩，但版本与契约在仓库内对齐  
- MVP 仍禁止引入 K8s / 自研论坛引擎  

### 备选方案

多仓库拆分：过早增加协作成本——否决。纯文档仓库无骨架：无法验证稳定性——否决。

## ADR-008: 校园邮箱会员、JSON 用户库与设备上限

- 状态: **Accepted**
- 日期: 2026-10-23
- 决策人: 项目负责人

### 背景

门户与管理端将作为两个 Zeabur 服务部署，磁盘不共享。需要校园身份门槛、一周试用、永久会员（文案 ¥19.9，本阶段不接支付），以及限制账号共享。浏览器拿不到 MAC 地址。

### 决策

1. 注册仅接受 `.edu.cn` / `.edu` 校园邮箱；验证后开始 7 天试用。
2. 用户数据由门户写入 `DATA_DIR/users.json`；管理端用共享 `INTERNAL_API_SECRET` 调用门户 `/api/internal/users` 发放/收回永久会员、踢设备。
3. 设备绑定使用客户端生成的 UUID（localStorage + cookie），每账号最多 2 台；**禁止采集 MAC**。
4. 文献关系网与发求助帖要求 `isEntitled`（试用未过期或永久）。图谱数据只用 OpenAlex 公开 API，交互参考「种子→邻域」，不复制商业产品界面。
5. 支付网关与 SMTP 本阶段不做；验证码可 `EMAIL_DEV_ECHO` 打日志，终身由管理员手工发放。

### 后果

- 双服务必须配置同一内部密钥；用户文件需挂在门户持久卷，并 gitignore `data/`。
- 设备限制可被清站点数据绕过，只作轻度防共享。
- 后续若接支付或 Postgres，新 ADR 标记本条部分字段 Superseded。

### 备选方案

- MAC 绑定：浏览器不可得且隐私风险——否决。
- 两服务各写一份用户文件：状态必然分叉——否决。
- 本阶段直接上微信/支付宝：范围过大——推迟。

## ADR-009: 可运行分析走门户作业，NCBI 上传只做到 L1

- 状态: **Superseded in part by ADR-010**
- 日期: 2026-11-03
- 决策人: 项目负责人

### 背景

工具目录（`catalog/tools`）只展示 YAML 卡片，不执行计算。转录组作图和 NCBI SRA 提交是下一批能力：前者要能在门户里跑完，后者容易滑向代传文件或代管私钥。

### 决策

1. 公开目录仍是工具卡。可运行分析另做门户路由，复用 `isEntitled`（校园邮箱已验证，且试用未过期或永久会员），不新建用户库。
2. 第一条作业是转录组 PCA：`/tools/rnaseq/pca` 上传矩阵和样本表后，门户同步调用 `services/rnaseq-viz` 的固定 CLI。参数只来自上传文件和白名单选项，不拼 shell，不运行用户脚本。
3. 小矩阵在请求内算完并落在 `DATA_DIR/jobs/`。队列 Worker 留到单次计算明显变长时再加。
4. 火山图、韦恩图、热图、GO 气泡图先以 `coming_soon` 卡片出现，不在本轮开放计算。
5. NCBI SRA 辅助的产品边界是 L1：校验 BioSample / SRA 模板（尚未实现）并给出 Aspera 命令说明。服务器不代理上传，不保存 Aspera 私钥或提交者密钥。

### 后果

- 会员门槛与文献关系网一致；未登录返回 401，无资格返回 402。
- PCA 依赖运行门户的环境里有 Python 3.11+。R 脚本是同一套参数的可选入口，镜像默认不装 R。
- 表达矩阵会短暂写到作业目录，成功后删除原始上传，保留图和得分表，并限制每个用户保留的作业份数。
- 后续若把作业改成队列，新 ADR 标记本条同步调用部分 Superseded。

### 备选方案

- 在浏览器里执行任意 R 脚本：否决（与 ToolHub「不执行任意代码」一致）。
- 由科研通服务器持有 Aspera 私钥并代传 FASTQ：否决（密钥与数据都不该落在平台上）。

## ADR-010: 转录组作业只收矩阵和分组

- 状态: **Accepted**
- 日期: 2026-11-03
- 决策人: 项目负责人

### 背景

ADR-009 把第一条作业做成单独的 PCA，并要求再上传样本表；火山图、韦恩图、热图、GO 仍是目录卡。这会变成让用户自己准备差异表和富集表的作图农场，和「上传矩阵就出下游结果」不一致。SRA 辅助如果只放一份手工清单，也没有形成作业。

### 决策

1. 可运行分析仍走门户作业，会员判断继续用 `isEntitled`。Worker 入口是 `python -m rnaseq_viz run`，门户同步调用它。
2. 输入合同只有两类：基因表达矩阵（基因 × 样本，TPM/FPKM），以及哪些列是对照、哪些列是处理组。QC、log2(x+1)、Welch 差异分析、PCA、火山图、热图、多处理组韦恩图都在同一次作业里完成，并打成 `results.zip`。
3. GO/KEGG 使用部署侧的物种 GMT（默认物种参数由页面给出）。库不存在时富集步骤明确失败，不改成向用户要富集表，其余图仍返回。
4. NCBI SRA 辅助是一次校验作业：BioSample 表、SRA metadata，加上运行时填写的邮箱、账号目录、私钥路径和数据目录。通过后返回 ascp 命令。门户使用 `--report-only`，不把私钥路径写入磁盘，也不执行 ascp，不代理 Submission Portal 登录。

### 后果

- `/tools/rnaseq/pca` 重定向到 `/tools/rnaseq`。旧的「只跑 PCA」接口返回 410。
- 注释库要单独部署；测试用迷你 GMT，不把生产注释提交进仓库。
- 本机 CLI 可以 `--execute` ascp；门户代码路径不传这个参数。
- ADR-009 里「不执行任意脚本、不在服务器保存 Aspera 私钥」仍然有效。

### 备选方案

- 继续按图种分别上传 DEG/GO 表：否决（输入不再最小）。
- 由门户保存私钥并代跑 ascp：否决（密钥和 FASTQ 不应留在平台上）。
